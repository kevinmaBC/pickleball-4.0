## 5. Module design (as implemented)

- **Entry points**: `PBAssessmentClassifier.loadConfig(base)` → `Promise<levelGatesJSON>` (fetches `level_gates_v2_3_1.json`, cross-checks `schema_version`/`benchmark_version` against `versions.json`, caches); `calculateCapabilityScore(componentScores)` → `number|null`, pure/sync; `classifyLevel(input, levelConfig)` → full result object, pure/sync, no config load required; `classifyTarget(input)` → resolves `levelConfig` from `input.target_level` against the loaded config; `validatedLevel(input)` → `{ validated_training_level, level_results }` across all 5 levels.
- **R1 rounding parity**: `roundHalfEven1(x)` decomposes the IEEE-754 double's exact bit pattern (sign/mantissa/exponent via `DataView`), reconstructs the exact rational value using `BigInt`, and rounds to 1 decimal with ties-to-even computed exactly (`2*remainder` vs `denominator` comparison) — no float-on-float rounding step anywhere. The capability-score arithmetic (`0.45*t + 0.30*d + 0.25*p`) is written in the identical left-to-right order as the Python source. Verified against 47 golden vectors including 15 deliberately-searched-for decimal-tie-proximity cases and boundary cases at every level's `capability_min ± {0, 0.05, 5, 5.05}` — **all match exactly**, both in Node and in the real browser.
- **Gate evaluation**: `metricPass()` mirrors `_metric_pass()` exactly — a metric key omitted from `metrics` (or explicitly `null`) is treated as `-Infinity` (`>=` gates) / `+Infinity` (`_max` gates), so a missing metric can never pass. `min_trials`/`min_sessions`/etc. fields present in `hard_gates` are read by neither this module nor the frozen Python reference (R2 — documented methodology debt below, not enforced).
- **Evidence**: `evidenceOk()` mirrors `evidence_ok()` exactly (rank comparison against `EVIDENCE_RANK`); an evidence value outside `{C1,C2,C3,C4}` throws `INVALID_EVIDENCE_CONFIDENCE` rather than silently coercing. `evidence_confidence` is read only as an explicit input field — never derived from any count/date/session data (the module has no access to any such data in the first place).
- **Classification**: `classifyCore()` mirrors `classify()`'s exact branch order and boundary semantics: `!evOk → LOW_CONFIDENCE`, else `(all gates pass AND cap>=min AND matchOk) → PASS`, else `(all gates pass AND |cap-min|<=5 AND matchOk) → BORDERLINE`, else `FAIL`. Because PASS is checked first, the borderline band is one-sided (below `capability_min` only) — verified explicitly (`S5-T33b`).
- **R3 result shape**: `classifyLevel()` wraps the minimal Python-shaped core result into the full `S5_DATA_CONTRACT.md` shape (`classifier_version`, `schema_version`/`benchmark_version` from the loaded config or `null`, `target_level`, `level_status`, `provisional_level` read from `levelConfig.status`, `capability_score_0_100`, `capability_min`, `component_scores`, `evidence{input,minimum,ok}`, `gate_results`, `match_validation{configured,required,min_match_transfer_score,input,ok}`, `missing_inputs`). Diagnostic fields (`gate_results`, `evidence.ok`, `match_validation.ok`) are `null` on `INCOMPLETE`, exactly matching the frozen Python's minimal early return for that branch while the numeric/status values stay parity-exact.
- **R4 borderline band**: the `5`-point band is a hardcoded literal in `classifyCore()`, matching the Python source's own hardcoded `5` rather than reading `statistical_policy.borderline_band_pp` from the JSON — the two are not wired together in either the frozen Python or this port (documented risk, unchanged from the frozen sources).
- **R5 non-contiguity**: `validatedLevel()` calls `classifyLevel()` independently for each of the 5 labels with no cross-level state, early exit, or lower-level-must-pass-first branch — confirmed both by design and by an explicit regression test (`tests/s5/validated_level.test.js` "R5" case) reproducing a genuine PASS-at-4.5-while-FAIL-at-3.0/3.5/4.0 result from the actual frozen configuration (4.5's `hard_gates` are disjoint from 4.0's — the only shared key is `ue_per_game_max`).
- **No scoring/inference beyond the frozen authority**: no evidence-confidence derivation, no S3-rate-to-metric mapping, no bottleneck ranking, no recommendation/prescription generation, no P0–P6/promotion logic, no DUPR interpretation exists anywhere in the module (statically enforced, `tests/s5/architecture_guard.test.js`). `data/prescription_rules_v2_3_1.json` was read only for S5-plan boundary awareness — no line of it was ported.
- **Determinism**: no `Date.now()`/`Math.random()`/iteration-order dependency anywhere; repeated calls with identical input are deep-equal (Node tests + real-browser proof).

## 11. Deviations / risks / notes

- **R2 methodology debt is real and unresolved by design**: any future consumer of `level_gates_v2_3_1.json`'s `hard_gates` sample-size fields (`min_trials`, `min_sessions`, `min_scenarios`, `min_rallies`, `min_opportunities`, `min_games`, `min_eligible_rallies`) must not assume S5 enforces them — it does not, matching the frozen Python reference exactly. This is a pre-existing gap in the frozen methodology itself, not introduced by S5.
- **R4 static/config-source discrepancy is real and unresolved by design**: `statistical_policy.borderline_band_pp` in the JSON (`5`) and the hardcoded `5` in both the frozen Python and this JS port currently agree, but are not wired together — a future JSON-only edit to `borderline_band_pp` would silently stop matching either implementation.
- **R7 legacy `app.js` divergence remains untouched**: `app.js:365`'s hardcoded second copy of what appear to be the 4.0-level thresholds (with `||0` missing-to-zero coercion) was neither modified, referenced, nor reconciled — confirmed by inspection that `js/assessment-classifier.js` shares no vocabulary or dependency with `app.js`.
